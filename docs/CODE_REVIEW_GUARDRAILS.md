# Code Review 自动护栏

这份文档说明本项目的自动检查系统怎么分工。目标很简单：机器先审机器，人只看结论和风险。

自动检查不是为了替代人，而是把格式错误、明显 bug、测试失败、影响范围这些重复劳动先筛掉。人最后判断：产品行为对不对、风险能不能接受、这次改动值不值得合并。

## 总体流程

1. AI 或开发者提交 PR。
2. 机器先跑基础检查：格式、lint、测试、影响分析、PR 规则。
3. 机器把问题写成清单：哪里错、为什么、严重程度、怎么复现。
4. 人只重点看三件事：高风险项、产品判断、机器无法判断的取舍。
5. 修完后再跑检查，直到结论清楚。

## 工具职责边界

### reviewdog / ruff

负责 Python 代码的低级质量检查：

- 语法、导入、未使用变量、常见风格问题。
- 把问题标到 PR 对应行，方便直接修。

它不负责判断需求是否做对，也不保证架构合理。ruff 通过，只能说明“没有发现它会检查的那类问题”。

### Danger

负责 PR 规则和流程提醒：

- PR 是否缺少说明。
- 是否改了高风险文件。
- 是否缺测试说明。
- 是否出现不该出现的改动范围。
- 是否需要人工确认。

Danger 更像门口的清单员，不是最终 reviewer。它能提醒风险，但不能替你决定产品行为。

### pytest

负责验证已有测试和新增测试：

- 单元测试、集成测试、回归测试。
- 确认这次改动没有破坏已覆盖的行为。

pytest 通过不代表没有 bug，只代表测试覆盖到的场景通过。没有测试覆盖的产品细节，仍然需要人工验收。

### GitNexus

负责代码关系和影响范围：

- 找某个函数、类、方法被谁调用。
- 看改动可能影响哪些执行流程。
- 在提交前检查实际影响是否符合预期。

本项目规则：修改代码符号前要先做影响分析；提交前要做变更检测。HIGH 或 CRITICAL 风险不能静默继续，必须让人确认。

GitNexus 也不是产品经理。它知道代码关系，不知道业务取舍是否正确。

### PR-Agent / on-demand AI review

负责按需做第二视角审查：

- 总结 PR 改了什么。
- 找潜在 bug、遗漏测试、可读性问题。
- 帮非代码用户理解风险。

它适合“再找一个 AI 看看”，但不能当最终批准人。AI review 的结论必须能落到证据：文件、行号、测试、复现步骤。

## 人应该看什么

人不需要重复机器已经检查过的格式问题。人应该重点看：

- 需求有没有被正确理解。
- 用户体验是否符合预期。
- 错误提示、边界场景、权限规则是否合理。
- 风险是否可以接受。
- 是否有“看似修好，其实绕过问题”的改法。

如果人看不懂代码，可以要求 AI 用中文解释每个风险，并给出“合并 / 不合并 / 需要再测”的建议。

## 合并前最低检查

合并前至少要有：

- PR 描述清楚：目标、改动、验证、风险。
- reviewdog / ruff 无未解释的失败。
- pytest 通过，或失败原因明确且与本 PR 无关。
- GitNexus 影响范围符合预期。
- 高风险改动已人工确认。
- 至少一次独立 review：人 review 或另一个 AI review。

任何一项缺失，都应该在 PR 里写明原因。

## 常见红灯

看到这些情况，先不要合并：

- 为了通过检查而跳过测试、删除断言、关闭 lint。
- PR 说明很短，但改动很多。
- AI 无法解释为什么改这些文件。
- 影响范围比需求大很多。
- 涉及权限、数据删除、支付、隐私、登录，但没有人工验收。
- 测试没有跑，却写“应该没问题”。

## 固定提示模板

### 只改一个目标

```text
你只负责一个目标：{目标}。
不要顺手修其他问题。
不要改无关格式。
如果发现必须扩大范围，先停下来说明原因和风险。
```

### 改前影响分析

```text
请先做改前影响分析，不要改代码。

目标：{要改的功能/函数/文件}
请说明：
- 相关代码在哪里。
- 直接调用方有哪些。
- 可能影响哪些流程。
- 风险等级是什么。
- 推荐跑哪些检查。
```

### 改后验收报告

```text
请给出改后验收报告：

1. 改了哪些文件。
2. 解决了哪个目标。
3. 跑了哪些检查，结果是什么。
4. 没跑哪些检查，为什么。
5. 剩余风险是什么。
6. 是否建议合并。
```

### 让另一个 AI 做 code review

```text
请作为独立 reviewer 审查这个 PR。

请只输出：
- 必须修复的问题。
- 建议修复的问题。
- 缺少的测试或验证。
- 可以合并 / 暂不合并 的建议。

不要只夸改动；没有问题也要说明剩余风险。
```

## 最后原则

机器负责尽早发现可自动判断的问题，人负责最终判断产品是否正确。把 AI 当成会加速的同事，不要当成会自动负责的负责人。
